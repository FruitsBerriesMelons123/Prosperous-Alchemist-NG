# Potion Prediction Defaults and Confirmed Baselines

## Purpose

This file is the canonical reference for potion-prediction settings, mod-enable combinations, and confirmed capture baselines. It contains three deliberately separate meanings of “default”:

1. **Default enabled-mod combination:** Vanilla Skyrim, with CACO disabled and Alchemy Plus disabled. This is the default when discussing which compatibility path is selected.
2. **Confirmed capture baseline:** the 14-row CACO-only baseline in `alchemist.potions-confirmed.csv`, plus the ten factor-one and ten ingredient-init recaptures. This is the strongest current observed-craft evidence, but it is not the default enabled-mod combination and is not a claim about every user's CACO configuration.
3. **Cross-mode default probes:** the additional CACO+AP, AP, and Vanilla rows in `alchemist.potions-confirmed.csv`, plus the ten CACO-enabled factor-one and ten ingredient-init recaptures. These establish representative default-mode controls; the CACO+AP Large Antlers order matrix and every completed CACO duration-family probe, including both `RestoreStaminaDuration` probes, are now complete.

The Alchemy Plus values in this document are copied from `SKSE\Plugins\AlchemyPlus.json`, which is currently using its upstream default values. The CACO and player values are the captured test baseline unless explicitly marked as a derived state or a mod-wide default.

Agents must read this file before planning a new potion capture or asking the user to change settings. Preserve the applicable default values below and list only intentional deviations. Do not silently turn the confirmed CACO capture baseline into the enabled-mod default.

The current Python accuracy gate is:

```text
python potion_prediction_test.py --check-confirmed-csv
```

The broad historical predicted-CSV suite remains deferred because its historical `potions-predicted-*.csv` fixtures are incomplete. New captures are generated by the plugin and added incrementally to the confirmed CSV; do not manually edit or blank the generated files. Check each capture against the applicable mode baseline or an explicitly documented deviation.

“Enabled” means the adapter is active for prediction, not merely that a DLL or JSON file exists. With the current Alchemy Plus defaults, `roundedPotency` and `impureCostFix` are enabled and make the AP adapter prediction-relevant. `knownFailureFix`, `mixtureNames`, and `copyExemplars` do not by themselves change the potion-value algorithm.

Do not call a test `CACO+AP`, `AP`, or `Vanilla` without stating both enabled/disabled states. In particular, do not call the CACO-only confirmed baseline the default plugin combination.

## Default player settings

These correspond to the confirmed CSV fields:

- **Alchemy level:** `100`
- **Fortify Alchemy level:** `0`
- **Alchemist perk rank:** `0`
- **Alchemist perk multiplier:** `1`
- **Physician:** disabled (`0`)
- **Benefactor:** disabled (`0`)
- **Poisoner:** disabled (`0`)
- **Purity:** disabled (`0`)
- **Seeker of Shadows:** disabled (`0`)
- **Concentrated Poison:** disabled (`0`)

These are runtime player-state inputs and are user-facing through the character's skill, equipment, and perks rather than through the CACO or Alchemy Plus JSON files. Alchemy level and Fortify Alchemy change potency; the Alchemist multiplier/rank and Physician, Benefactor, Poisoner, Purity, and Seeker of Shadows can change applicable effect potency or which effects remain. `AlchemistPerkMultiplier` takes precedence over the rank fallback in the current profile. `ConcentratedPoison` is captured for compatibility and weight behavior but is not currently believed to change potion gold prediction.

### Note about testing defaults
- Switching modes (e.g. from CACO to CACO+AP) requires exiting and restarting Skyrim. Every time the user starts Skyrim they create a new character. In most cases the user does not need to be told to manually reset any settings. This should help you be more appropriate in helping the user.

### Note about non-default settings and user instructions
- When presenting test plans, requests, or instructions (or directly to the user), agents MUST explicitly inform the user that they **only need to modify settings or files that are NON-DEFAULT**.
- Do NOT flood test instructions with full lists of default settings that do not require user action. Clearly separate and highlight only the non-default settings or deviations.
- **Simple Chat Presentation:** Test instructions in user responses MUST specify non-default settings in a clean, simple way without referencing script output blocks, execution logs, or internal script mechanisms.
- **Python Script Change-Only Output:** Python mode scripts MUST only print output when a variable was actually changed on disk, formatted as: `<variable>: default = <default_val>, previous = <prev_val>, changed to = <new_val>`.
- **Agent Requirement for On-Disk Settings & MO2 Profile:** Whenever planning or executing a test batch that requires non-default on-disk settings, MO2 enabled mod changes (`modlist.txt`), or load order file restoration (`plugins.txt`, `loadorder.txt`, `lockedorder.txt` from backups), agents MUST update or create the root Python mode scripts (`pat-vanilla.py`, `pat-caco.py`, `pat-ap.py`, `pat-caco-ap.py`, `pat_config_helper.py`, or indexed variants like `pat-caco-2.py`, `pat-caco-ap-2.py`) directly with the target parameters so the user can simply run the script to stage all necessary disk and MO2 profile modifications without hand-editing files.
- **In-Game State Applied by `pat` Commands:** Player skill level (e.g. Alchemy 100 or 50), Fortify Alchemy, perks, GameSettings, and globals are applied automatically in-game by the custom `pat` console commands (and indexed variants like `pat caco 2`, `pat caco 3`). Do NOT instruct the user to set alchemy level using the Developer Test Hub.

### Note about multi-block testing and full-session batching
- **Multi-Block Console Commands:** For a single Skyrim game session under a specific mode, multiple runtime setting blocks can be executed sequentially in-game via indexed `pat` subcommands (e.g., `pat caco`, `pat caco 2`, `pat caco 3`, `pat caco-ap`, `pat caco-ap 2`, `pat vanilla`). This avoids restarting Skyrim for runtime-only parameter changes.
- **Pre-Launch Python Scripts:** On-disk configurations (`AlchemyPlus.json`, MO2 `modlist.txt`) are applied before launching Skyrim via root Python scripts (`pat-<mode>-<num>.py` or `pat-<mode>.py`).
- **Full-Session Batching:** When providing test instructions to the user, agents MUST compile all necessary test blocks, create test CSVs (e.g., `specific-test-1.csv`), update Papyrus test handlers (`ProsperousAlchemistTests.psc` / `pa-tests.yaml`) and pre-launch Python scripts, compile via `compile.ps1`, and deploy `alchemist.dll` upfront. Provide the user with complete instructions for the full testing session before awaiting test execution results.

### Note about alchemist.ini
- The variables `Player`, `CACO`, and `AlchemyPlus` are only reports and do not actually change any settings in-game. It is probably not appropriate for you to modify them yourself.

### CACO setting ownership and current prediction impact

The following classifications describe the current adapter and Python model, not a claim that every CACO release exposes every field in the same UI. “User-facing” means a setting exposed through CACO's MCM or another normal in-game UI. A live game setting/global or record can still be a runtime input that another mod, console command, or external test setup changes without being user-facing.

| Setting | User-facing/modifiable? | Currently believed to affect prediction? | Current understanding |
|---|---|---|---|
| `AlchemyIngredientInitMultiplier` | No direct in-game control; runtime Skyrim game setting `fAlchemyIngredientInitMult` | **Yes** | Changes CACO alchemy effectiveness, which changes constructed magnitudes/durations and their costs. The adapter reads the live game setting; it is not a CACO MCM option. |
| `AlchemySkillFactor` | No direct in-game control; runtime Skyrim game setting `fAlchemySkillFactor` | **Yes** | Changes the skill-dependent CACO effectiveness multiplier and therefore effect values and potion cost. The adapter reads the live game setting; it is not a CACO MCM option. |
| `AlchemyXPMultiplier` | Yes; CACO MCM/global | **No immediate price effect** | Changes alchemy XP behavior. It is captured for completeness, but the current potion-value model does not treat it as a current-potion cost multiplier. |
| `RestoreHealthDuration`, `RestoreMagickaDuration`, `RestoreStaminaDuration` | Yes; CACO MCM/global | **Yes, conditionally** | Selects the 1-second, 5-second, or 10-second CACO effect variant for the matching restore family; the selected input can change crafted effects and cost. |
| `DamageHealthDuration`, `DamageMagickaDuration`, `DamageStaminaDuration` | Yes; CACO MCM/global | **Yes, conditionally** | Selects the matching CACO damage-family duration variant and can change crafted effects and cost. |
| `RestoreEffectsDoNotStack` | No independent setting in the current adapter; derived from loaded CACO restore effect records | **Not directly** | Preserve it as captured compatibility metadata. The predictor uses the active effect records; it does not currently expose this boolean as an independent calculation switch. |
| `DisableAllPotionHandling` | Yes; CACO MCM | **Unsupported (Must be 1)** | Disables CACO's post-craft handling. MUST ALWAYS be `1` (potion handling disabled). Scripted potion handling is buggy, slow, fails automated detection, and is unsupported. |
| `ImpurePotionProcessing` | Yes; CACO MCM | **Unsupported (Must be 0)** | CACO 20% post-craft impure adjustment. MUST ALWAYS be `0` (disabled). Scripted potion handling is buggy, slow, fails automated detection, and is unsupported. |

`RestoreEffectsDoNotStack` and `AlchemyXPMultiplier` must remain in exported settings JSON even when they do not currently change the value algorithm. They are useful for proving that a capture used the intended live setup.

`AlchemyIngredientInitMultiplier` and `AlchemySkillFactor` must also remain in exported settings JSON because they affect prediction, but they should be treated as captured runtime inputs rather than ordinary user-facing CACO settings. A capture that changes either value must document the game-setting override or other test setup used to change the live value.

#### Modifying AlchemySkillFactor and AlchemyIngredientInitMult in-game
- For interactive manual console entry by human users, use the console commands `setgs fAlchemySkillFactor <val>` and `setgs fAlchemyIngredientInitMult <val>`.
- **In Papyrus test scripts (e.g. `ProsperousAlchemistTests.psc`)**: use `ConsoleUtil.ExecuteCommand("setgs <setting> <value>")`, as implemented by the test script. Papyrus does not provide a `Utility.SetGameSettingFloat` function; do not use that nonexistent API.

### Alchemy Plus setting ownership and current prediction impact

Every field in `AlchemyPlus.json` other than `$comment` is user-modifiable in the JSON file. The first three feature toggles are user-facing Alchemy Plus behavior; only the entries identified below as prediction-relevant are currently part of the potion-value model.

| Setting | User-facing/modifiable? | Currently believed to affect prediction? | Current understanding |
|---|---|---|---|
| `knownFailureFix.enabled` | Yes | **No** | Changes the UI's known-failure display between ingredients; it does not change effects, potency, or gold value. |
| `mixtureNames.enabled` | Yes | **No** | Changes crafted mixture names; it does not change the value-bearing effect calculation. |
| `impureCostFix.enabled` | Yes | **Yes, conditionally** | The current adapter makes qualifying impure effect contributions subtract from the total before finalizing gold. This is Alchemy Plus's signed-cost behavior, not CACO's 20% post-processing rule. |
| `copyExemplars.enabled` | Yes | **No direct value effect** | Changes the model/name selected for a crafted potion using the configured exemplar list; the current predictor does not use it as a cost formula. |
| `copyExemplars.exemplars` | Yes | **No direct value effect** | Changes the candidate exemplar forms used by Alchemy Plus. Keep the list in captures for configuration identity, but do not treat it as a potion-price input. |
| `roundedPotency.enabled` | Yes | **Yes, conditionally** | Enables magnitude and duration rounding before the constructed effect contribution is calculated. It can change effect values, shared-effect priority, and gold. |
| `roundedPotency.magnitudeThreshold` / `magnitudeMult` | Yes | **Yes when a magnitude exceeds the threshold** | With the defaults, a magnitude greater than `25.0` is rounded to a multiple of `5.0`. |
| `roundedPotency.durationThreshold` / `durationMult` | Yes | **Yes when a duration exceeds the threshold** | With the defaults, a duration greater than `15.0` is rounded to a multiple of `5.0`. |
| `roundedPotency.overrides` | Yes; advanced per-effect map | **Yes for matching effects** | An effect-specific threshold or multiple replaces the corresponding global value. The default map has no actual overrides. |

The Python harness now loads an explicit JSON path and the active profile snapshot using the same supported prediction-affecting fields. The settings that are currently believed to change potion prediction are therefore: CACO alchemy effectiveness, CACO duration variants, CACO handling/impurity, Alchemy Plus impure-cost correction, Alchemy Plus potency rounding, and the player alchemy/perk state below. UI-only, naming, model, XP, and derived metadata must not be mistaken for value-algorithm inputs.
